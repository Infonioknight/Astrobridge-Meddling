One correction — it's not "a random tile," it's "every overlapping tile pair." With no RA/Dec filter specified, you didn't get one arbitrary tile — the crossmatch processes the entire overlap between the two catalogs: it compares GZ10's full tile map against SDSS's full tile map, identifies every pair of tiles that spatially overlap (could be hundreds or thousands of pairs, exactly matching that "2732 partitions" progress bar you saw earlier), and only skips tile pairs with zero overlap. The randomness you noticed isn't about which tile got selected — it's about which of those many overlapping tile-pair results happens to finish computing and stream back to you first. Full determinism in what gets compared, nondeterminism only in arrival order.

Filling in the vague part — what happens inside one overlapping tile pair:

## Step 1: Load just those two tiles' worth of objects (this is the whole efficiency win — you're never touching tiles that don't overlap).

### Step 2: Building a spatial index (KD-tree) — why you need it at all
Say the overlapping SDSS tile has 50,000 spectra in it. If for every GZ10 galaxy you just looped through all 50,000 SDSS objects computing the distance to each one, that's 50,000 distance calculations per galaxy — brutally slow even within one small tile.
A KD-tree fixes this by pre-organizing those 50,000 points into a structure you can search efficiently. The intuition: it recursively splits the points in half. First split: find the median RA among all 50,000 points, put everything left of that median in one branch, everything right in the other. Within each branch, split again — but now by declination, using the median Dec of that branch. Keep alternating RA/Dec splits, halving the group each time (50,000 → 25,000 → 12,500 → ...), until each leaf holds just a handful of points.
The payoff: to find what's near a given point, you don't check all 50,000 — you walk down the tree (is my point left or right of this split? left or right of the next split?) in roughly log₂(50,000) ≈ 16 steps to land near the right neighborhood, then only check a small local cluster of candidates instead of everything. This is why nearest-neighbor search on the tree is roughly O(log N) instead of O(N) per query — the tree gets built once per tile (a one-time cost), and then every subsequent nearest-neighbor lookup against it is cheap.
(Small technical note: since RA/Dec are angles on a sphere, not a flat plane, LSDB actually builds the tree in 3D Cartesian coordinates converted from the sky positions — this avoids distortion near the poles and wraparound issues at RA=0°/360°, but the tree logic itself is the same idea.)

### Step 3: Querying the tree — one lookup per left-catalog object
Now the tree exists for this SDSS tile. For every single GZ10 galaxy in the overlapping GZ10 tile, you ask the tree one question: "what SDSS point is closest to this GZ10 galaxy's position?" The tree walk finds that answer in ~16 comparison steps instead of 50,000. This repeats for every GZ10 galaxy in that tile — say there are 8,000 of them — so you get 8,000 candidate nearest-neighbor pairs out of this one tile-pair comparison, each pair carrying an actual angular distance (how far apart the two matched points really are on the sky).
At this point, you have 8,000 GZ10-SDSS pairs, but nothing has checked yet whether those pairs are good matches — the tree will happily hand you "the closest thing," even if the closest thing is 10 arcminutes away and clearly a different galaxy.

### Step 4: Applying your filters — deciding which candidates survive
This is where radius_arcsec and n_neighbors actually do their work, and they do different jobs:

radius_arcsec is a validity cutoff. Out of those 8,000 candidate pairs, throw away any pair whose distance exceeds your threshold (default 1 arcsecond). If a GZ10 galaxy's nearest SDSS point happens to be 5 arcseconds away, that's not a real match — SDSS just doesn't have a genuine spectrum for that particular galaxy — so that GZ10 galaxy drops out of the result entirely. This is why your crossmatch output has fewer rows than GZ10 alone: some galaxies simply fail this check.
n_neighbors is a quantity cap, applied separately, per surviving GZ10 object. With n_neighbors=1, you keep only the single closest SDSS match per galaxy (the one you already found in Step 3). If you'd set n_neighbors=3, the tree query in Step 3 would instead return the three closest SDSS points per galaxy, and each of those three would go through the same radius_arcsec check independently — so you might end up with 1, 2, or 3 surviving matches per galaxy, depending how many of its nearest candidates are actually within range.

So the full pipeline per tile-pair, in order: build tree once (Step 2) → for each left-object, pull its N nearest right-object candidates (Step 3) → drop any candidate beyond the distance threshold (Step 4) → whatever survives becomes rows in your crossmatch result. Dask runs this whole four-step sequence independently and in parallel across every overlapping tile-pair, then hands you back the combined set of surviving pairs — which is the deterministic result set you're streaming from.
